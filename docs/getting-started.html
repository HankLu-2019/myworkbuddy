MyWorkBuddyField guide for a first run

0 of 0 steps done

    Hands-on tour · about 2–3 hours, in sittings

    Run MyWorkBuddy on your VM and try every part of it

    Read one step, do it, tick it. The steps go in the order a new team would meet the product: start it, set it up as an admin, use it as a member, then take a Jira ticket all the way to a merge request.

    Start with fake mode

    The stack runs with the same stand-ins the test suite uses: a fake AI model, a fake GitLab, Jira and RSS feed. Every feature works, nothing leaves the VM, nothing costs money.

    Parts 1–6 · no credentials needed

    Then switch to real mode

    Point it at AWS Bedrock, your GitLab or Gerrit and Jira, add TLS and gVisor. Answers become real and slower; the flows stay the same.

    Part 7 · needs Bedrock and tokens
    Part 1

    Start it

    You need a Linux VM (Ubuntu 24.04 or Debian 12) with Docker Engine 27 or later and the Compose plugin, about 8 GB of RAM and 40 GB of free disk. The sandbox image alone is several GB.

    1.1

    Get the code

    2 min

    The four newest pull requests (Insights, containers in verification, single sign-on, MCP servers) aren't on main yet. Until they're merged, use the branch that has all of them.

    git clone https://github.com/HankLu-2019/myworkbuddy.git /opt/myworkbuddy
cd /opt/myworkbuddy
git checkout feat/f12-mcp   # after #47–#50 are merged: git checkout main
    1.2

    Write the settings file for fake mode

    3 min

    This makes a .env with a fresh encryption key and passwords, plain HTTP on port 8080, and runc as the sandbox runtime (fine for a trial; Part 7 switches to gVisor).

    cp .env.example .env && chmod 600 .env
key=$(python3 -c "import base64,os;print(base64.urlsafe_b64encode(os.urandom(32)).decode())")
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$(openssl rand -hex 16)|; \
s|^MWB_SECRET_KEY=.*|MWB_SECRET_KEY=$key|; \
s|^MWB_HOSTNAME=.*|MWB_HOSTNAME=http://localhost:8080|; \
s|^MWB_TLS_MODE=.*|MWB_TLS_MODE=none|; \
s|^MWB_COOKIE_SECURE=.*|MWB_COOKIE_SECURE=false|; \
s|^LITELLM_MASTER_KEY=.*|LITELLM_MASTER_KEY=sk-$(openssl rand -hex 16)|; \
s|^LITELLM_DB_PASSWORD=.*|LITELLM_DB_PASSWORD=$(openssl rand -hex 16)|; \
s|^MWB_SANDBOX_RUNTIME=.*|MWB_SANDBOX_RUNTIME=runc|; \
s|^MWB_RUNNER_TOKEN=.*|MWB_RUNNER_TOKEN=$(openssl rand -hex 24)|" .env
    Keep a copy of .env. Without MWB_SECRET_KEY, the tokens people store can't be decrypted.
    1.3

    Build the sandbox image

    10–15 min

    This is the container the coding agent and the verification commands run in: Python, Go, Node and a pinned Claude Code, with no credentials inside.

    docker build -t mwb-sandbox:latest sandbox

    If it fails on a download (Go, uv), run it again: those are network hiccups.

    1.4

    Start the stack with the fakes

    5–10 min

    compose.ci.yml swaps the AI gateway for the fake one, which also plays GitLab, Jira and a status feed at http://llm-gateway:4000 inside Docker.

    alias mwb-compose='docker compose -f docker-compose.yml -f compose.ci.yml'
mwb-compose up -d --build --wait
mwb-compose ps
    You should see

    Every service running or healthy, and migrate exited with code 0.

    1.5

    Create your admin and open the app

    2 min
    mwb-compose exec api mwb create-admin --username admin --email you@example.com
# it asks for a password: at least 10 characters

    The app is on port 8080 of the VM. From your laptop, tunnel it so the address matches MWB_HOSTNAME:

    ssh -L 8080:localhost:8080 you@your-vm

    Then open http://localhost:8080 in your browser.

    Part 2

    Set it up as the admin

    An admin connects the company systems once. People then add their own tokens, so everyone only ever sees what they could see themselves.

    2.1

    Sign in and check System

    3 min
    1. Sign in as admin. Home shows an admin setup checklist.
    2. Open Admin → System.
    You should see
    • Database, AI gateway and worker checks green, background job queues, disk space, AI spend this month.
    • Sandboxes: the runner ready. It warns that the runtime is runc (expected in fake mode) and that verification with containers isn't available (no Sysbox).
    System is where you'll look first whenever something seems off: every block reports on its own, so one broken part doesn't hide the rest.
    2.2

    Connect the fake GitLab, Jira and a status feed

    5 min

    Open Admin → Integrations → Add integration three times:

    KindNameURLExtra
    GitLabGitLabhttp://llm-gateway:4000
    JiraJirahttp://llm-gateway:4000
    RSS/Atom feedsStatus feedhttp://llm-gateway:4000Feed URLs: http://llm-gateway:4000/fake/feed.xml

    Plain http is accepted only because fake mode allows it. In real mode, any self-hosted https server works (any host and port; paste the company CA if it uses one), and an internal server without TLS can be allowed by name with MWB_HTTP_INTERNAL_HOSTS.

    2.3

    Add yourself as a member

    2 min

    Use a separate member account for the rest of the tour, because members and admins see different things. Open Admin → Users → Add user, name it erin, and copy the one-time password it shows (it's shown once).

    While you're there, look at the budget column: every user has a monthly AI budget, enforced by the gateway.

    Part 3

    Use it as a member: knowledge and chat

    Sign out, then sign in as erin in a private window so you can switch between the two accounts.

    3.1

    First sign-in and Getting started

    3 min
    1. Sign in with the one-time password; you're asked to choose your own right away.
    2. Confirm your time zone when Home asks. Schedules and Insights use it.
    3. Home now shows a Getting started checklist that ticks itself as you go.
    3.2

    Add your tokens and test them

    3 min

    Settings → Integrations. For each integration, paste a token and press Test:

    • GitLab: glpat-trial-token (any token starting glpat- works; glpat-readonly… pretends it can't push)
    • Jira: jira-trial-token (anything starting jira-)
    You should see

    "Verified" next to each. Tokens are write-only: you can replace or remove one, never read it back.

    3.3

    Add a repository and watch it index

    3 min

    Sources → Repositories → Add repository, with URL http://llm-gateway:4000/fake/git/team/payments.git and the GitLab integration.

    You should see
    • Progress (queued → running → ready), then counts of files, code chunks and docs.
    • A project card in your wiki that sums up the repository.
    • A Conventions box: rules for the planner and agent, for repositories without their own AGENTS.md or CLAUDE.md.
    Indexing is what lets chat and the planner answer with your code, not general knowledge. It's private until you choose Share with team.
    3.4

    Ask chat a question

    3 min

    Open Chat → New chat and ask "How are webhooks delivered in payments?"

    You should see
    • A tool call to search_knowledge, then a streamed answer with a citation [1]. In fake mode the wording is a fixed sentence; the plumbing is real.
    • Click the citation: the source opens beside the chat. The cost of the answer is shown under it.
    3.5

    Upload a document, search, and share

    5 min
    1. Sources → Documents: drop in a Markdown or PDF runbook.
    2. Search for a word from it. Results mix documents, code and wiki pages, ranked by meaning and by exact words together.
    3. On the document, Share with team, then sign in as admin and search for it there. Then Make private and check that it disappears for admin.
    Private by default is the main promise of the knowledge base. Try to break it here: a document someone didn't share should never show up in another person's search, chat or plans.
    3.6

    Look at the wiki and your memory

    3 min

    Wiki holds Markdown pages in git: yours, and a team space. Create a page, edit it, open History to see the diff.

    Every chat session gets a short summary; a nightly librarian (02:00 your time) folds those into me/how-i-work.md, which chat reads to know how you work. Check Wiki → Changes tomorrow to see what it wrote, and revert anything you don't like.

    Part 4

    Let it watch things for you

    4.1

    Have chat propose a schedule

    3 min

    In a new chat, write: "Check the payments namespace every weekday morning and tell me only if something's wrong."

    You should see

    "I've proposed a schedule for that." and a card with the check, the time in your time zone, and Create. Chat never creates a schedule on its own; you click.

    4.2

    Make a morning brief and run it now

    5 min
    1. Schedules → New schedule. Name it "Morning brief", check type Morning brief, and pick the status feed.
    2. Create schedule, then Run now.
    3. Open the Inbox.
    You should see
    • A run result "1 new item(s) in the status feed" with findings and links.
    • An inbox item. Run it again: no new item, because it notifies only when something changed.
    • Investigate in chat opens a chat that already has the run as context.
    4.3

    Optional: get notified in Slack or Teams

    5 min

    Needs a real incoming-webhook URL and outbound HTTPS from the VM. Settings → Notifications → Add channel: pick the app, paste the URL, choose what to send, then Send test.

    The URL is a secret: after saving you only ever see a hint like hooks.slack.com/…abcd. Messages carry the title and a link back; details stay out unless you tick Include the first lines of each item.

    Part 5

    Take a ticket to a merge request

    This is the main flow: Jira ticket → plan you approve → an agent writes the change in a locked-down sandbox → you review the diff → push and merge request. Nothing is pushed or posted without an approval of the exact content.

    5.1

    Put a ticket on the Board

    2 min

    Board → Add ticket, Jira key PROJ-123. The fake Jira answers any key with "Retry webhook delivery on 5xx".

    On the card, choose the repository payments, then Draft plan.

    5.2

    Review, revise and approve the plan

    5 min
    1. Review plan. Read the summary, the files it will change, tests, verification commands, risks and the sandbox request.
    2. Type feedback ("Give up after three attempts and log the event id.") and press Revise with feedback.
    3. Revision 2 arrives with "Changed from revision 1: …". Open the comparison.
    4. Tick any warnings it asks you to acknowledge, then Approve revision 2.
    The plan is the contract. Validation checks that files exist at the base commit, that protected paths and CI files are flagged, and that the commit message starts with the Jira key. Your approval binds the exact content of the revision you approved.
    5.3

    Start the job and watch it work

    5 min

    On the ticket's Job tab, press Start job. Follow the timeline: preparing → running (the agent) → verifying (the plan's commands) → awaiting review. Jobs in the sidebar lists everything running.

    You should see
    • The agent's steps streaming in, then each verification command with its exit code and log.
    • A checks list: secrets scan, file size, changed lines, protected paths, files outside the plan.

    To see where it runs: docker ps --filter label=mwb.job. The container has no credentials, a read-only root, no Linux capabilities, and reaches the outside only through the egress proxy.

    5.4

    Review the change and push it

    5 min
    1. Read the diff (split or unified). If it's not right, Request changes with a note; the agent tries again in the same workspace.
    2. When it is, Review push. The preview shows exactly what will happen: the branch, commit message, merge request title and body, and the Jira comment.
    3. Push branch and open merge request.
    You should see

    "Pushed" with links Merge request and Jira comment, and "Watching for merge."

    5.5

    Simulate a failing pipeline, a review comment and the merge

    10–25 min

    On real GitLab these happen by themselves. In fake mode you trigger them. Define a small helper on the VM:

    fake() { mwb-compose exec -T api python -c "import sys,urllib.request as u; u.urlopen(u.Request('http://llm-gateway:4000'+sys.argv[1], data=(sys.argv[2] if len(sys.argv)>2 else '{}').encode(), method='POST', headers={'content-type':'application/json'}))" "$@"; }

    A failing pipeline. Then wait up to 10 minutes (pushed jobs are checked every 10 minutes); the job shows the failure, and you get an inbox item.

    fake /fake/pipeline '{"mr_iid":1,"status":"failed","jobs":[{"name":"unit","stage":"test","status":"failed","log":"AssertionError: retries == 0"}]}'

    Press Fix CI failure, add a note if you like. A new round starts from the pushed change, with the failing log as untrusted input.

    A reviewer's comment.

    fake /fake/discussion '{"mr_iid":1,"body":"Please log the event id when giving up.","path":"app/webhooks.py","line":3}'

    Press Address review comments, pick the thread, and later approve the reply that gets posted to it.

    The merge.

    fake /fake/merge/1
    You should see

    Within 10 minutes the job is "Merged", and a Change document appears in your knowledge (search for "merged"). The planner uses past changes of the same repository the next time.

    5.6

    Things to notice along the way

    reading
    • The agent can ask. When a plan is unclear, a job pauses with a question, shown on Home and under Jobs → Waiting for you. Answer it and it carries on (at most 3 questions a job).
    • A failed push can be retried from the Job tab without starting over.
    • A CI failure can become a ticket. On a CI failures schedule result, Create ticket on a finding drafts the Jira issue, and can draft its plan right away. Needs a Jenkins or GitLab CI integration, so try it in real mode.
    Part 6

    See how it's going, and the admin extras

    6.1

    Open Insights

    3 min

    Insights (under Work) shows the jobs started in a period: how they ended, attempts and review rounds per job, median time from start to review and from push to merge, and AI cost per merged change and per week. Each chart has Show table.

    As admin, switch Whose jobs to "Everyone's". Members only ever see their own.

    6.2

    Register an MCP server (read-only tools)

    5 min

    The fake gateway is also an MCP server. Fake mode allows plain http, so as admin: Admin → Integrations → Add MCP server.

    • Name docs, URL http://llm-gateway:4000/mcp
    • Auth header Authorization, value Bearer mcp-secret
    You should see
    • Six tools, all off. create_ticket and purge_cache say "Write tool: can't be turned on".
    • Turn on for search_docs asks why it's needed and why it only reads, and shows the description and schema the model will see.
    • Members' chats now offer mcp.docs.search_docs to the model. The fake model sticks to knowledge search, so you'll see it used in real mode. Its answers are treated as untrusted data (the fake server's answer even contains "Ignore previous instructions", on purpose).
    6.3

    Single sign-on (real mode)

    20 min

    Needs your company's identity provider. Register a client with redirect URI <MWB_HOSTNAME>/api/auth/oidc/callback, then set MWB_OIDC_ISSUER, MWB_OIDC_CLIENT_ID, MWB_OIDC_CLIENT_SECRET and restart. The sign-in page gains Sign in with SSO.

    • A member whose verified email matches an account is linked once, then matched by the provider's ID only.
    • Admin accounts are never linked by email. Link yours yourself: Settings → Profile → Link SSO.
    • MWB_LOCAL_LOGIN=admins turns passwords off for members; admins keep theirs as a fallback.
    6.4

    Verification with containers (needs Sysbox)

    30 min

    For repositories whose tests need a database in Docker. Install Sysbox on the VM, then:

    docker build -f sandbox/Dockerfile.dind -t mwb-sandbox-dind:latest sandbox
# .env: MWB_PROXY_REGISTRY_HOSTS=<your registry mirror>, then:
mwb-compose up -d runner

    System's Sandboxes block should say "available (Sysbox installed)". As admin, turn on Verification with containers on the repository page. A plan can then ask for it, and you'll see it in the plan and in the approval.

    This part hasn't run on a real VM yet. Please try a plan whose verification runs docker compose up -d postgres, and run the sandbox security tests from an inner container (design 04 §9, tests 1–3).
    Part 7

    Switch to real mode

    The same stack, without compose.ci.yml. Do it on a fresh database, or keep the trial data. The fake integrations simply stop answering, so remove them.

    7.1

    Point it at Bedrock and your systems

    20 min

    In .env, set:

    • AWS_REGION, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, and the model IDs MWB_CHAT_MODEL_ID, MWB_FAST_MODEL_ID, MWB_EMBED_MODEL_ID (planner and coder default to chat), or an OpenAI-compatible endpoint instead.
    • MWB_HOSTNAME=https://…, MWB_TLS_MODE=files with deploy/tls/cert.pem and key.pem (or internal), MWB_COOKIE_SECURE=true.
    • MWB_SMTP_* for email.
    • Self-hosted servers without TLS: MWB_HTTP_INTERNAL_HOSTS=gitlab.local,*.corp.internal. System then warns that tokens to them aren't encrypted in transit.

    Optional: keep the secrets key in HashiCorp Vault. With the compose Vault:

    docker compose --profile vault up -d vault
deploy/vault/init.sh          # prints the unseal key, root token and the .env lines, once
# add MWB_SECRETS_BACKEND=vault and the MWB_VAULT_* lines to .env, restart api worker worker-jobs, then:
docker compose exec api mwb rotate-secrets
docker compose exec api mwb vault status

    After every restart of the VM, Vault is sealed and MyWorkBuddy won't start until you run deploy/vault/unseal.sh. System → Stored secrets shows where the key lives.

    Install gVisor, register runsc with Docker, then set MWB_SANDBOX_RUNTIME=runsc.

    docker run --rm --runtime=runsc hello-world
docker compose -f docker-compose.yml up -d --build --wait
docker compose exec api mwb llm check   # the gateway can create and delete a user key
    7.2

    Run the real checklists

    1–2 h

    These are the checks nothing automated can do. They're in docs/implementation-plan.md, one per phase:

    • Chat answers in English and Chinese with citations; a real GitLab and a real Gerrit repository indexed; backup and restore drill.
    • A real Kubernetes health check alerts on a crash-looping test pod, stays quiet the next time, then says "recovered".
    • A real ticket → plan → job → push on a test repository, on GitLab and on Gerrit, with gVisor.
    • A failing pipeline fixed with Fix CI failure; a reviewer's comment addressed and replied to; a CI failure turned into a ticket; a Slack or Teams message; a teammate signing in with SSO.
    If something's off

    Where to look

    What you seeLook at
    A service won't startmwb-compose ps -a, then mwb-compose logs --tail 50 migrate api. Logs are JSON, one event per line.
    The repository stays "failed"Repository page shows the error and what to do; check the URL and that the token tested OK.
    Jobs fail right awaySystem → Sandboxes; docker images mwb-sandbox; mwb-compose logs runner egress-proxy.
    Nothing happens after a pushPushed jobs are checked every 10 minutes; the worker must be healthy (System).
    Disk filling upSystem → Disk; job workspaces are removed after review, and docker system df.
